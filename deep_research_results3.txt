Architecting a Resilient Offline-First Audio Synchronization Platform: Overcoming OAuth, Rate-Limiting, and Quota BarriersThe development of media-rich web applications utilizing vanilla web technologies—specifically HTML5, CSS3, and JavaScript—interfacing with serverless execution environments presents a unique and highly complex set of architectural challenges. When applications rely heavily on third-party application programming interfaces (APIs) such as the Spotify Web API and YouTube audio extraction libraries, developers frequently encounter severe structural friction points. These operational bottlenecks typically manifest as stringent OAuth 2.0 security constraints, aggressive anti-bot countermeasures targeting datacenter IP addresses, and restrictive usage quotas on real-time cloud databases.The application under analysis, "okMUSIC," operates as a companion utility requiring the seamless ingestion of Spotify playlist metadata and the subsequent retrieval of corresponding audio streams from YouTube, ultimately storing these heavy media assets locally within the browser context. The current operational architecture (Version 5) relies on a Vercel-hosted serverless backend utilizing the play-dl library for media extraction, Firebase Realtime Database for state synchronization, and standard Spotify OAuth workflows for identity management. This implementation has encountered critical structural failures, defined as "Hard Walls," which completely stall application functionality. These failures include Spotify authentication rejections due to uniform resource identifier (URI) mismatches, HTTP 403 Forbidden errors when attempting to bypass authentication via guest modes, aggressive YouTube CAPTCHA blocks against Vercel IP ranges, and Firebase database disabled states due to exceeded free-tier bandwidth and connection quotas.This comprehensive research report delineates a definitive "Master Architecture Document" for Version 6 (V6) of the system. It provides an exhaustive analysis of the underlying causes of these failures and proposes robust, production-ready solutions designed to decouple the frontend from fragile backend dependencies. The proposed architecture transitions the system from a brittle, synchronous, server-dependent application into a resilient, offline-first, decentralized media platform. Key strategic implementations include establishing a federated audio extraction pipeline to bypass datacenter IP bans entirely, implementing an IndexedDB-centric local-first data layer with deferred cloud synchronization, and instituting an adaptive authentication model utilizing unauthenticated oEmbed fallbacks alongside secure cross-domain proxy workflows.1. Resolving the Spotify Identity and Metadata EcosystemThe ingestion of playlist metadata relies fundamentally on the Spotify Web API. The existing implementation faces two distinct and critical failure modes: chronic "Invalid Redirect URI" errors during the OAuth 2.0 Authorization Code flow, and HTTP 403 Forbidden responses when attempting to bypass the user login requirement using the Client Credentials grant type. Addressing these issues requires a complete restructuring of how the application handles identity, token exchange, and cross-domain routing.1.1 Deconstructing the Redirect URI MismatchThe OAuth 2.0 specification strictly requires the authorization server to redirect the user-agent back to the client using a pre-registered URI after access has been granted or denied. The Spotify authorization server enforces rigorous string matching for the redirect_uri parameter. The authorization handshake will consistently fail if the URI provided in the application code deviates by even a single character—including trailing slashes, port numbers, or varying protocol schemes (HTTP versus HTTPS)—from the exact URI whitelisted within the Spotify Developer Dashboard.When deploying applications to platforms like GitHub Pages or Vercel, developers often utilize dynamic subdomains, branch preview URLs, and forced trailing slash rewrites. A common anti-pattern involves utilizing window.location.origin dynamically as the redirect URI in the client-side JavaScript. While this functions perfectly in a local development environment (e.g., http://localhost:3000), it frequently fails in production because the resulting dynamic origin may not exist in the static Spotify dashboard whitelist. Furthermore, attempting to whitelist every possible dynamic branch preview URL is administratively impossible and presents security vulnerabilities.To eradicate the redirect URI mismatch permanently, the architecture must decouple the dynamic frontend origin from the static OAuth callback mechanism. This is achieved by designating a single, static serverless function endpoint on the primary backend proxy domain (e.g., a dedicated Vercel route like https://okmusic-proxy.vercel.app/api/auth/callback) as the absolute, unchanging redirect_uri.The implementation workflow for this centralized authentication proxy operates as follows. First, the developer must register exactly one production URI in the Spotify Dashboard, regardless of where the frontend is currently hosted. Second, when the frontend initiates the OAuth flow, it explicitly passes this static URI to Spotify. To remember where the user originated—whether on a GitHub Pages domain, a local testing server, or a Vercel preview branch—the frontend encodes its current URL into the OAuth state parameter, generating a secure payload.Once the user approves the authorization, Spotify redirects the user to the centralized Vercel serverless function. The Vercel function extracts the authorization code, exchanges it securely for an access_token and refresh_token using the stored client_secret, and then inspects the state parameter to determine the original frontend destination. Finally, the serverless function performs an HTTP 302 redirect back to the originating frontend URL, appending the generated tokens securely as URL hash fragments (e.g., #access_token=...&refresh_token=...). Hash fragments are mathematically secure for this cross-domain transfer because the browser does not transmit hash fragments to the server in subsequent HTTP requests, keeping the tokens strictly within the client-side JavaScript execution context.Architectural ComponentLegacy Implementation (V5)Master Architecture (V6)Strategic AdvantageRedirect URI SourceDynamic (window.location.origin)Static Vercel Serverless FunctionEliminates character mismatch and trailing slash errors entirely.Token ExchangeClient-side (Exposes Secret)Server-side Vercel ProxySecures client_secret within Vercel environment variables.State ParameterUnused or randomized stringEncoded Origin URL PayloadAllows seamless cross-domain routing back to GitHub Pages or localhost.Token DeliveryQuery ParametersURL Hash FragmentsPrevents token leakage in server access logs and HTTP referer headers.1.2 Bypassing the 403 Forbidden Wall and Guest Mode LimitationsThe attempt to utilize the "Client Credentials" flow to bypass the user login requirement (often termed "Guest Mode") is fundamentally incompatible with the current requirements for user-specific data retrieval. The Client Credentials grant type is strictly designed for server-to-server authentication to access non-user-specific endpoints, such as general artist catalogs or album releases.Furthermore, on November 27, 2024, Spotify implemented severe restrictions on the Web API, fundamentally altering the developer landscape. Access to several critical endpoints, including audio features and the ability to fetch public playlists acting generically as the user spotify, was completely deprecated or placed behind stringent quota extensions requiring manual corporate approval. Consequently, fetching /playlists/{id}/tracks using a generic Client Credentials token will result in an immediate HTTP 403 Forbidden error, or return a payload where the track arrays are undefined, as the API now strictly isolates user-generated content behind user-authorized contexts.To reliably scan a playlist containing vast numbers of tracks without strictly forcing a full OAuth login for every guest user, the application must abandon the traditional Web API for unauthenticated requests and adopt a dual-layer hybrid scanning strategy.For public playlists, the system can bypass the standard Web API entirely by utilizing Spotify's oEmbed infrastructure. The oEmbed API is an open standard designed to generate rich link previews for third-party platforms. By fetching the HTML representation of a Spotify track or playlist via the oEmbed endpoint, the response payload contains a serialized JSON script block with comprehensive track metadata, including artist names, track titles, and even embedded audio previews. Because this infrastructure is intended for public web consumption and scraping by social media platforms, it does not require an OAuth access token, thereby perfectly satisfying the "Guest Mode" requirement without triggering 403 errors.For users who wish to import private playlists or bypass rate limits imposed on public endpoints, the application dynamically falls back to the Authorization Code Flow utilizing the previously established cross-domain Vercel proxy.1.3 Robust Vanilla JavaScript Spotify Scanner ImplementationThe following JavaScript implementation, specifically designed for the V6 App single-class architecture, demonstrates a highly resilient scanning module. It systematically attempts authenticated fetches if a token is present in the local storage, automatically handles token expiration by executing refresh workflows, and fundamentally utilizes the oEmbed scraping technique for unauthenticated public playlist extraction.JavaScript/**
 * Master Architecture V6: Spotify API Interaction Module
 * Designed for a Vanilla JS Single-Class Architecture.
 * Handles both authenticated pagination and unauthenticated oEmbed extraction.
 */
class SpotifyScanner {
    constructor(clientId, proxyDomain) {
        this.clientId = clientId;
        this.proxyDomain = proxyDomain; // e.g., https://okmusic-proxy.vercel.app
        this.apiBase = "https://api.spotify.com/v1";
    }

    /**
     * Entry point to resolve a playlist. Evaluates local authentication state.
     * Initiates public oEmbed extraction if no valid session exists.
     */
    async scanPlaylist(playlistId) {
        const accessToken = localStorage.getItem('spotify_access_token');
        
        if (accessToken) {
            try {
                return await this.fetchAuthenticatedPlaylist(playlistId, accessToken);
            } catch (error) {
                if (error.status === 401) {
                    console.warn("OAuth Token expired. Initiating background refresh sequence...");
                    const refreshed = await this.refreshAccessToken();
                    if (refreshed) {
                        return await this.fetchAuthenticatedPlaylist(playlistId, localStorage.getItem('spotify_access_token'));
                    }
                }
                console.error("Authenticated data retrieval failed. Executing oEmbed fallback.", error);
                return await this.extractPublicPlaylistMetadata(playlistId);
            }
        } else {
            console.log("No authorization token detected. Utilizing Guest Mode (oEmbed Extraction).");
            return await this.extractPublicPlaylistMetadata(playlistId);
        }
    }

    /**
     * Standard Web API fetch utilizing OAuth Tokens.
     * Incorporates automatic pagination for playlists exceeding 100 tracks.
     */
    async fetchAuthenticatedPlaylist(playlistId, token) {
        let tracks =;
        let nextUrl = `${this.apiBase}/playlists/${playlistId}/tracks?limit=100`;

        while (nextUrl) {
            const response = await fetch(nextUrl, {
                headers: { 'Authorization': `Bearer ${token}` }
            });

            if (!response.ok) throw { status: response.status, message: await response.text() };

            const data = await response.json();
            if (!data.items) throw new Error("Track array undefined - possible API privacy restriction or deprecation.");

            // Map the required metadata to the application's internal data model
            const mappedTracks = data.items.map(item => ({
                id: item.track.id,
                title: item.track.name,
                artist: item.track.artists.map(a => a.name).join(', '),
                duration: item.track.duration_ms
            }));

            tracks = tracks.concat(mappedTracks);
            nextUrl = data.next; // Proceed to the next pagination cursor if it exists
        }
        return tracks;
    }

    /**
     * Circumvention for 403 / Guest Mode utilizing Spotify's public embed payloads.
     * Routes through the Vercel proxy to neutralize Browser CORS restrictions.
     */
    async extractPublicPlaylistMetadata(playlistId) {
        try {
            // Proxied through Vercel to avoid strict CORS blocks on open.spotify.com
            const proxyUrl = `${this.proxyDomain}/api/proxy-embed?id=${playlistId}`;
            const response = await fetch(proxyUrl);
            
            if (!response.ok) throw new Error("Public extraction proxy encountered an upstream failure.");
            
            const html = await response.text();
            
            // Extract the serialized JSON script payload injected natively by Spotify
            const scriptRegex = /<script id="resource" type="application\/json">(.*?)<\/script>/s;
            const match = html.match(scriptRegex);
            
            if (!match ||!match) throw new Error("Failed to locate metadata payload within DOM.");
            
            const payload = JSON.parse(decodeURIComponent(match));
            
            // Validate the payload structure before mapping
            if (!payload.tracks ||!payload.tracks.items) {
                 throw new Error("Invalid oEmbed payload structure.");
            }

            return payload.tracks.items.map(item => ({
                id: item.track.id,
                title: item.track.name,
                artist: item.track.artists.map(a => a.name).join(', '),
                duration: item.track.duration_ms
            }));
        } catch (error) {
            console.error("Guest mode extraction critically failed. Playlist is likely private.", error);
            throw new Error("Cannot fetch playlist. Please log in to import private playlists.");
        }
    }

    /**
     * Refresh Token logic communicating with the Vercel Proxy.
     * Ensures session continuity without requiring user intervention.
     */
    async refreshAccessToken() {
        const refreshToken = localStorage.getItem('spotify_refresh_token');
        if (!refreshToken) return false;

        try {
            const response = await fetch(`${this.proxyDomain}/api/auth/refresh`, {
                method: 'POST',
                headers: { 'Content-Type': 'application/json' },
                body: JSON.stringify({ refresh_token: refreshToken })
            });

            if (response.ok) {
                const data = await response.json();
                localStorage.setItem('spotify_access_token', data.access_token);
                if (data.refresh_token) {
                    localStorage.setItem('spotify_refresh_token', data.refresh_token); // Update if a new one is issued
                }
                return true;
            }
        } catch (error) {
            console.error("Token refresh sequence failed.", error);
        }
        
        // If the refresh sequence fails (e.g., token revoked by user), clear local state
        localStorage.removeItem('spotify_access_token');
        localStorage.removeItem('spotify_refresh_token');
        return false;
    }
}

Circumventing Aggressive Datacenter Bot ProtectionThe most critical functional bottleneck in the current V5 architecture involves the extraction of audio streams via the play-dl library hosted directly on Vercel's serverless infrastructure. Requests originating from Vercel execute within major cloud provider datacenters, primarily utilizing underlying AWS regions such as iad1 located in Washington, D.C.. This geographic and infrastructural centralization is fundamentally incompatible with modern scraping techniques.2.1 The Anatomy of YouTube's IP Bans and Library FailuresYouTube, operated by Google, employs highly sophisticated, continuously evolving anti-bot countermeasures to protect its infrastructure from automated scraping, server-side downloading, and denial-of-service vectors. These security systems evaluate traffic patterns primarily through the analysis of the requesting IP address's Autonomous System Number (ASN). Datacenter ASNs belonging to Amazon Web Services, Google Cloud Platform, and DigitalOcean are assigned inherently low trust scores by YouTube's firewall.When a serverless function executing play-dl attempts to initialize a download stream, YouTube's active protection systems intercept the request and return an HTTP 429 Too Many Requests or HTTP 403 Forbidden response, invariably accompanied by the HTML payload: "Sign in to confirm you're not a bot. This helps protect our community".Attempting to bypass this limitation by rotating standard HTTP User-Agent headers, randomizing referers, or injecting browser-specific headers is completely insufficient, as the primary vector of the block remains the datacenter ASN. Furthermore, while some developers attempt to circumvent this by injecting Netscape-formatted cookies.txt files generated from authenticated, residential browser sessions into play-dl , this approach introduces extreme fragility. Authentication cookies expire rapidly, become actively invalidated by Google if used simultaneously from geographically disparate IP addresses (e.g., a home residential IP in Europe and an AWS datacenter IP in Virginia), and present severe security risks if the serverless function environment is ever compromised or exposed.2.2 Alternative Streaming Architectures: API FederationTo achieve a foolproof, resilient download logic that will not trigger catastrophic blocks, the architecture must abandon the execution of direct scraping libraries (such as play-dl or ytdl-core) entirely within the Vercel datacenter. Instead, the backend must leverage decentralized, community-maintained extraction networks. These federated networks continuously proxy and rotate their extraction endpoints through vast pools of residential IPs or high-trust IPv6 subnets, effectively absorbing the bot-protection friction. Two prominent solutions emerge for this specific architectural requirement: The Cobalt API and the Piped API.The Cobalt API Paradigm:
Cobalt is an advanced, high-efficiency media downloader that acts as an intelligent proxy specifically designed to bypass aggressive platform protections. The Cobalt API utilizes a modular architecture that accepts a simple JSON payload containing the target URL and specific configuration flags, such as youtubeBetterAudio: true and isAudioOnly: true. Cobalt instances automatically handle the underlying stream decryption, cipher signature routing, and bot-challenge circumvention, returning a direct, unthrottled URL to the processed audio stream.The Piped API Paradigm:
Piped operates as a privacy-friendly YouTube frontend and API alternative, engineered to serve content efficiently without communicating directly with Google's tracking infrastructure from the client side. The Piped API provides a highly reliable, unauthenticated /streams/:videoId endpoint. Upon receiving a request, the API processes the YouTube video and returns a deeply structured JSON object containing an array of audioStreams. This payload details exact bitrates, specific codecs (e.g., mp4a.40.5), and direct playback URLs that bypass standard tracking mechanisms.API ArchitectureOperational MechanismAudio Output QualityRate Limiting Profileplay-dl (Local)Direct datacenter scrapingVariable (Requires FFMPEG)Blocked instantly via ASN detection.Cobalt APIIntelligent proxy routingHigh (youtubeBetterAudio)Moderate (Requires instance rotation).Piped APIFederated proxy networkExplicit (mp4a.40.5 at 128kbps)Low (Distributed across numerous instances).The Master Architecture (V6) mandates a federated approach. The system will dynamically query a public Piped API instance (or a self-hosted Cobalt instance), extract the direct audio URL, and meticulously pipe that URL through the Vercel backend. This proxying is mandatory to mask the client's IP and satisfy aggressive browser Cross-Origin Resource Sharing (CORS) requirements that would otherwise block direct downloads.2.3 Constructing the Resilient Node.js Streaming PipelineServerless functions operate under strict computational constraints, including strict memory limits (often a 250 MB unzipped maximum size) and rigid execution timeouts (typically 10 seconds on free tiers). Attempting to download an entire 10MB audio file directly into the Vercel function's volatile memory buffer before sending it to the client browser will result in catastrophic memory exhaustion (Out of Memory errors) and unacceptably high latency.The optimal architectural approach utilizes Node.js Streams to process the data incrementally. HTTP response streaming allows the Vercel serverless function to incrementally send chunks of the audio file to the client browser exactly as they are received from the upstream federated provider. This methodology ensures a Time To First Byte (TTFB) measured in milliseconds and requires virtually zero memory overhead on the Vercel server, preventing execution limits from becoming a bottleneck.By utilizing the native Node.js stream.pipeline module, the system elegantly manages "backpressure". Backpressure occurs when the upstream source delivers data significantly faster than the downstream client connection can download it. The pipeline methodology automatically pauses the upstream read stream, ensuring no data is lost or buffered unnecessarily in the server's memory.The following Vercel Serverless Function replaces the failing play-dl logic entirely. It utilizes the Piped API to locate the media, extracts the highest quality audio stream, and pipes the MPEG blob natively to the client.JavaScript/**
 * Vercel Serverless Function: /api/fetch.js
 * Master Architecture V6: Resilient Audio Stream Proxy
 * Neutralizes YouTube Datacenter Blocks via Piped API Federation and Node.js Streaming
 */
import { pipeline } from 'node:stream/promises';
import fetch from 'node-fetch';

export default async function handler(req, res) {
    if (req.method!== 'GET') {
        return res.status(405).json({ error: 'Method Not Allowed' });
    }

    const { query } = req.query;
    if (!query) {
        return res.status(400).json({ error: 'Missing search query parameter.' });
    }

    // A list of public Piped instances. 
    // In production environments, an array of instances should be rotated to prevent rate limiting.
    const pipedApiBase = 'https://pipedapi.kavin.rocks'; 

    try {
        // Step 1: Execute search query against the federated Piped API
        const searchResponse = await fetch(`${pipedApiBase}/search?q=${encodeURIComponent(query)}&filter=music_songs`);
        if (!searchResponse.ok) throw new Error('Search execution failed on upstream provider.');
        
        const searchData = await searchResponse.json();
        const firstResult = searchData.items.find(item => item.type === 'stream');
        
        if (!firstResult) {
            return res.status(404).json({ error: 'No audio track located for the given query.' });
        }

        const videoId = firstResult.url.split('/watch?v=');

        // Step 2: Extract the granular stream metadata
        const streamResponse = await fetch(`${pipedApiBase}/streams/${videoId}`);
        if (!streamResponse.ok) throw new Error('Stream metadata extraction failed.');
        
        const streamData = await streamResponse.json();
        
        // Step 3: Filter for the optimal audio-only stream (prioritizing MP4A/M4A codecs)
        const audioStreams = streamData.audioStreams.sort((a, b) => b.bitrate - a.bitrate);
        if (audioStreams.length === 0) throw new Error('No compatible audio streams available.');
        
        const targetStreamUrl = audioStreams.url;

        // Step 4: Initiate the fetch against the actual audio stream URL
        const audioFetch = await fetch(targetStreamUrl);
        if (!audioFetch.ok) throw new Error(`Upstream audio fetch failed: ${audioFetch.statusText}`);

        // Step 5: Configure HTTP Response Headers for Native Browser Streaming
        // These headers are essential for the browser to recognize the incoming blob as an audio file
        res.setHeader('Content-Type', audioStreams.mimeType |

| 'audio/mp4');
        res.setHeader('Content-Disposition', `attachment; filename="${encodeURIComponent(firstResult.title)}.m4a"`);
        res.setHeader('Cache-Control', 'public, max-age=86400'); // Cache at the Vercel Edge for 24 hours
        
        // If the upstream provider provides an accurate content length, pass it down to enable progress bars
        const contentLength = audioFetch.headers.get('content-length');
        if (contentLength) {
            res.setHeader('Content-Length', contentLength);
        }

        // Step 6: Pipe the upstream readable stream directly to the Vercel writable response
        // `pipeline` automatically manages memory backpressure and safely closes streams upon completion or error
        await pipeline(audioFetch.body, res);

    } catch (error) {
        console.error('Streaming pipeline encountered a critical error:', error);
        // Ensure error responses are only sent if the stream headers haven't already been dispatched
        if (!res.headersSent) {
            res.status(500).json({ error: 'Internal Server Error during stream extraction and piping.' });
        }
    }
}
3. Designing an Offline-First State with IndexedDBThe third critical structural failure point lies deeply within the application's data layer. Relying on Firebase Realtime Database (RTDB) for real-time metadata synchronization has resulted in frequent "Database Disabled" errors. This operational halt occurs because the application is continually reading and writing every individual track ingestion state to the cloud simultaneously, rapidly exhausting Google's free-tier bandwidth and connection limits.3.1 The Limitations of Firebase Realtime Database on the WebWhile Firebase RTDB provides excellent, low-latency data synchronization for actively connected online applications, its official web SDK fundamentally lacks robust offline disk persistence capabilities. Although the RTDB client can temporarily queue writes in volatile memory while a network connection is briefly lost, it cannot permanently persist data to the hard drive across browser reloads or extended offline periods on the web client. If the application initializes while offline, or if the Firebase quota is exceeded (effectively simulating a permanent offline state from the client's perspective), the application's data layer becomes completely unusable, resulting in catastrophic failure for the end-user.3.2 Establishing a Local-First Paradigm with Dexie.jsTo successfully engineer a resilient "Offline-First" web application, the fundamental data architecture must be inverted. The cloud database can no longer act as the primary Single Source of Truth (SSOT). Instead, the user's browser must be elevated to act as the primary SSOT, utilizing the native IndexedDB API. In an offline-first paradigm, all Create, Read, Update, and Delete (CRUD) operations execute instantaneously against the local database on the client's device, entirely eliminating network latency and the need for synchronous loading spinners.Interacting directly with the low-level IndexedDB API is notoriously complex and error-prone due to its callback-heavy, event-driven design and complex cursor management. Therefore, the architecture will integrate Dexie.js, a minimalist, highly optimized wrapper that provides a robust, promise-based interface for IndexedDB. Dexie.js handles database versioning, schema upgrades, and complex transactional queries natively, allowing the vanilla JavaScript frontend to interact with the local storage as if it were a modern NoSQL database.By storing both the track metadata and the raw audio blobs (represented as ArrayBuffer or Blob objects) directly within Dexie.js, the application achieves 100% core functionality without requiring any active network connection.3.3 Architecting the Custom Synchronization EngineTo maintain cross-device capability without exhausting Firebase quotas, Firebase RTDB must be structurally demoted from a primary database to an asynchronous, deferred synchronization transport layer. The system will employ a "Last-Write-Wins" Conflict-Free Replicated Data Type (CRDT) logic, a methodology commonly used in complex offline-first systems to ensure eventual consistency without requiring server-side locking mechanisms.The synchronization strategy dictates several strict operational rules. All application writes occur purely and instantly in Dexie.js. A background process, operating independently of the main UI thread, listens to the browser's navigator.onLine status and Firebase's internal .info/connected state to determine true network availability. When the connection is definitively verified and the Firebase quota is determined to be active, the application executes a batch synchronization process. It retrieves all local records modified since the last successful sync timestamp, packages them into a single payload, and pushes them to Firebase.Crucially, the heavy audio blobs (which can easily exceed several megabytes per track) are never uploaded to Firebase. Only the lightweight metadata and the unique Spotify IDs are synced to the cloud. When a user logs into okMUSIC on a completely new device, the metadata is pulled down from Firebase, and the application subsequently utilizes the background Piped API proxy to silently re-download the audio blobs directly to the new device's IndexedDB. This architecture preserves cloud storage limits while ensuring seamless cross-device functionality.The following Vanilla JavaScript snippet outlines the structural foundation of this Dexie-to-Firebase synchronization module.JavaScript/**
 * Master Architecture V6: Offline-First Synchronization Engine
 * Manages local IndexedDB state via Dexie.js and defers cloud writes to Firebase RTDB.
 */
import Dexie from 'https://cdn.jsdelivr.net/npm/dexie@3.2.4/dist/dexie.mjs';

class OfflineFirstDatabase {
    constructor(firebaseDatabaseRef) {
        this.firebaseDb = firebaseDatabaseRef;
        this.db = new Dexie('okMUSIC_DB');
        
        // Define Database Schema
        // ++id represents an auto-incrementing primary key managed by Dexie
        // The properties listed in the string are indexed for fast, optimized searching
        this.db.version(1).stores({
            playlists: '++id, spotifyId, title, lastModified, syncStatus',
            tracks: '++id, playlistId, title, artist, lastModified, syncStatus',
            audioBlobs: 'trackId' // Media blobs are heavy; only index by the relational trackId
        });

        this.initSyncListeners();
    }

    /**
     * Primary interface for the Application to save an ingested track.
     * Executes instantly against local storage, providing zero-latency UI updates.
     */
    async saveTrackLocally(playlistId, trackData, audioBlob) {
        const timestamp = Date.now();
        
        // Execute an atomic transaction to ensure data integrity between metadata and blobs
        return await this.db.transaction('rw', this.db.tracks, this.db.audioBlobs, async () => {
            const localTrackId = await this.db.tracks.add({
                playlistId: playlistId,
                title: trackData.title,
                artist: trackData.artist,
                spotifyId: trackData.id,
                lastModified: timestamp,
                syncStatus: 'pending' // Explicitly flagged for future background sync
            });

            // Store the heavy MPEG blob in a separate, isolated table
            await this.db.audioBlobs.add({
                trackId: localTrackId,
                data: audioBlob
            });

            console.log(`Track securely saved locally. Internal ID: ${localTrackId}`);
            
            // Attempt an immediate background sync if the network appears online
            this.attemptBackgroundSync();
            
            return localTrackId;
        });
    }

    /**
     * Initializes passive event listeners for network restoration to trigger the deferred sync queue.
     */
    initSyncListeners() {
        window.addEventListener('online', () => {
            console.log("Browser reports network restoration. Triggering deferred sync queue...");
            this.attemptBackgroundSync();
        });

        // Firebase-specific active connection monitoring
        if (this.firebaseDb) {
            this.firebaseDb.ref('.info/connected').on('value', (snap) => {
                if (snap.val() === true) {
                    this.attemptBackgroundSync();
                }
            });
        }
    }

    /**
     * Asynchronous synchronization processor.
     * Extracts all records flagged as 'pending' and executes a batched push to Firebase.
     */
    async attemptBackgroundSync() {
        if (!navigator.onLine ||!this.firebaseDb) return;

        try {
            // Retrieve all unsynced tracks using Dexie's optimized where clause
            const pendingTracks = await this.db.tracks.where('syncStatus').equals('pending').toArray();
            
            if (pendingTracks.length === 0) return;

            const updates = {};
            pendingTracks.forEach(track => {
                // Prepare a flat batch update for Firebase to minimize discrete network requests
                // Note: The heavy audioBlob is intentionally omitted to preserve cloud quotas.
                updates[`/users/currentUser/tracks/${track.spotifyId}`] = {
                    title: track.title,
                    artist: track.artist,
                    lastModified: track.lastModified
                };
            });

            // Execute an atomic multi-path update in Firebase RTDB
            await this.firebaseDb.ref().update(updates);

            // Upon verifiable successful cloud write, update local status to 'synced'
            await this.db.transaction('rw', this.db.tracks, async () => {
                for (let track of pendingTracks) {
                    await this.db.tracks.update(track.id, { syncStatus: 'synced' });
                }
            });

            console.log(`Successfully synchronized ${pendingTracks.length} metadata records to Firebase.`);
        } catch (error) {
            console.warn("Background sync encountered an error. Data remains safely isolated in IndexedDB.", error);
            // Errors frequently involve quota exhaustion. The status remains 'pending' for infinite future retries.
        }
    }
}
